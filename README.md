# Personal Internet Watchtower

> 一个替你巡逻互联网、而不是把你留在互联网里的个人信息展示板。

中文名暂定：**聚合视界 / 个人互联网瞭望塔**

---

## 为什么做这个项目

很多注意力并不是被“真正想看的内容”消耗掉的，而是被一种反复确认的冲动消耗掉的：

- 隔一会儿打开 NGA，看看常逛的板块有没有新帖、热帖；
- 看看自己的回复有没有收到回复、点赞或 @；
- 顺手打开 B 站，看看关注的 UP 有没有更新、主播有没有开播；
- 再去龙空看看最近又在讨论什么；
- 打开这些 App 之后，又很容易顺手刷几下推荐流；
- 原本正在做的事情被打断，注意力被切成碎片。

Personal Internet Watchtower 想解决的不是“如何让我看到更多内容”，而是：

> **我本来就会去这几个地方，你替我定时去看。只有真的发生了值得我知道的事情，再告诉我。**

理想状态下，用户只需要偶尔打开一个页面：

- 有值得看的内容 → 点击，跳回原网站；
- 没有值得看的内容 → 关闭页面，继续手头的事情。

这个页面本身不应该成为新的内容消费场所。

---

## 核心理念

### 1. Dashboard，而不是 Reader

本项目不是传统 RSS Reader。

我们并不优先关心：

- 跨设备阅读进度；
- 完整浏览历史；
- 长期收藏体系；
- 在聚合页面内阅读全文；
- 构建一个新的内容消费 App。

我们更关心：

- **现在有没有新东西？**
- **有没有和我有关的事情发生？**
- **我常去的地方有没有值得点进去看的讨论？**
- **我关注的人有没有更新或开播？**

---

### 2. 替用户“检查”，而不是替用户“刷”

目标不是把 NGA、B站、龙空重新做一遍。

聚合页面只承担三个动作：

1. 定时检查；
2. 判断哪些变化值得展示；
3. 提供原始链接。

真正的阅读、回复、观看仍然发生在原网站。

---

### 3. 只看用户主动选择的地方

这是本项目最重要的边界之一。

如果用户只添加了：

- NGA；
- Bilibili；
- 龙空；

那么系统就只从这些地方获取信息。

即使互联网上还有 Reddit、YouTube、贴吧等相关内容，系统也**不应该主动扩大信息来源**。

只有当用户自己说：

> “最近我也开始经常看这个贴吧。”

它才应该被加入瞭望塔。

**系统的职责是减少需要检查的地方，而不是不断扩大“值得检查的世界”。**

---

### 4. 可以便捷地增加、暂停和删除“瞭望点”

人的上网习惯会变化。

今天常逛 NGA、B站、龙空，未来可能加入：

- 贴吧；
- 某个小众论坛；
- YouTube；
- 某个社区；
- 某个博客或 RSS。

因此，“增加一个新地方”不应该意味着修改主程序。

每个站点通过独立 Connector / Adapter 接入，主程序只消费统一的数据结构。

同样，删除一个论坛也应该足够简单：

> 停止检查 → 清除对应配置/凭据 → 页面中消失。

---

### 5. 不做无限滚动

无限信息流和本项目的目标天然冲突。

首页应该是**有限的、有结束的**。

例如：

- 和我有关：5 条；
- 关注更新：10 条；
- 值得看看：5 条。

看完以后，可以明确地得到一个结论：

> **“现在没有别的值得你知道的事情了。”**

这是功能，不是缺陷。

## 计划中的核心功能

### 站点检查

不同站点可以实现不同能力，例如：

**NGA**

- 指定板块新帖；
- 指定板块热帖；
- 我的回复是否收到新回复；
- @ / 点赞 / 其他账户相关事件（需验证可行性）。

**Bilibili**

- 关注 UP 主是否更新；
- 关注主播是否开播；
- 关注动态；
- 可选的站内兴趣发现，例如“AI”相关视频。

**龙空**

- 指定板块新讨论；
- 指定板块热帖；
- 指定帖子更新。

未来可以继续增加贴吧、YouTube、其他论坛等。

---

## 关于“发现”

本项目允许有限的主动发现，但必须遵守两个约束：

1. **只能发生在用户已经添加的数据源内部；**
2. **必须由用户主动启用。**

例如：

> 用户已经把 B 站加入瞭望塔，并主动添加 “AI” 标签。

系统可以在 B 站内部综合：

- 发布时间；
- 播放量；
- 一段时间内的播放增长；
- 收藏、点赞、投币、评论等互动指标；

发现近期可能值得看的 AI 视频。

它不应该因此自动跑去 YouTube、Reddit、贴吧继续寻找 AI 内容。

### 为什么需要短期指标历史

“10 万播放”本身并不足以说明内容正在变热。

更有价值的信号可能是：

```text
09:00  2,000
10:00  3,500
11:00  7,000
12:00 15,000
```

因此系统可能需要少量本地存储，用于保存短期指标快照。

这些数据用于判断“变化”，而不是建立复杂的阅读历史。

## 技术方向

当前倾向：

```text
                 Internet

        ┌──────────┼──────────┐
        │          │          │
       NGA        B站        龙空
        │          │          │
        ├─ RSSHub / API / RSS ┤
        │          │          │
        └── Custom Connector ─┘
                   │
                   ▼
            Normalized Events
                   │
            Ranking / Filtering
                   │
                   ▼
                SQLite
                   │
                   ▼
              Dashboard UI
                   │
                   ▼
            点击 → 原始网站
```

优先复用成熟项目：

- **RSSHub**：作为大量站点的数据适配层；
- **Glance**：作为 Dashboard 设计和首版 UI 的重要参考，是否直接作为前端底座待验证；
- 对登录态、反爬或账户级事件，再编写少量 Custom Connector。

原则是：

> 能复用的采集能力尽量复用，真正自己维护的是“统一事件、筛选逻辑、短期指标与展示”。

## Connector 设计原则

主程序不应该写死 NGA、B站、龙空。

每个站点只是一个 Adapter，例如：

```text
connectors/
  bilibili/
  nga/
  lkong/
  tieba/
  generic-rss/
```

一个 Connector 可以只实现自己能够实现的能力：

```text
latest
hot
following_updates
live_status
account_events
search
metrics
```

并不是每个站点都必须支持所有能力。

这样未来新增一个论坛时，主要工作应该是：

> 新增一个 Connector，而不是修改整个系统。

详见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)。

---

## 明确不做什么

至少在项目早期，我们有意不做：

- 全网内容搜索；
- 自动扩展数据源；
- 无限推荐流；
- “猜你喜欢”式黑盒推荐；
- 社交网络；
- 评论系统；
- 在本项目内观看/阅读全文；
- 重型的阅读历史和同步系统；
- 为了“功能完整”而加入大量配置项。

如果一个功能会让用户在这个页面停留得更久，而不是减少主动检查 App 的次数，就应该非常谨慎。

详见 [docs/PRODUCT_PRINCIPLES.md](docs/PRODUCT_PRINCIPLES.md)。

## 阶段规划

### Phase 0 — 可行性验证

目标：确认真实使用场景和数据获取能力。

优先验证：

- NGA 指定板块新帖 / 热帖；
- NGA 账户相关事件；
- B站关注 UP 更新；
- B站主播直播状态；
- 龙空指定板块更新；
- 登录态 / Cookie 的稳定性；
- RSSHub 能覆盖多少，哪些必须自己写 Connector。

### Phase 1 — 最小可用版本

目标：做出一个自己愿意每天打开的页面。

包含：

- NGA / B站 / 龙空三个初始数据源；
- 有限数量的卡片；
- 自动刷新；
- 点击跳转原站；
- 简单的添加 / 删除 / 暂停数据源；
- 本地配置与凭据管理。

### Phase 2 — “和我有关”

目标：减少对原 App 的主动检查。

重点：

- NGA 回复 / @ / 点赞等事件；
- B站关注动态与直播；
- 更稳定的账户登录态；
- “为什么出现这条内容”的清晰说明。

### Phase 3 — 站内发现（实验性）

目标：验证“有限主动发现”是否有价值。

第一批实验：

- B站 AI 标签；
- 视频指标定时采样；
- 播放增长 / 互动率；
- 非黑盒、可解释的简单排序。

该阶段必须继续遵守：

> 不自动扩展信息源。

### Phase 4 — Connector 扩展

目标：让增加 / 删除常逛网站变得低成本。

候选：

- 贴吧；
- YouTube；
- 更多论坛；
- 通用 RSS；
- 其他具有稳定 API / RSSHub route 的站点。

详细规划见 [docs/ROADMAP.md](docs/ROADMAP.md)。

## 项目成功的判断标准

这个项目是否成功，不看：

- 用户刷了多少条内容；
- 页面停留了多久；
- 推荐点击率有多高。

而看：

> **它是否减少了用户一天中主动打开多个 App、反复刷新和确认“有没有新东西”的次数。**

如果打开 Watchtower 后看到：

> 暂时没有值得你看的新东西。

然后放心地关掉网页继续工作——这正是我们想要的结果。
